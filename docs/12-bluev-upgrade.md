# 12 蓝V（企业号）升级路径 —— 能力解锁规划

> 状态（2026-10-12）：**只规划、不编码**。触发条件满足（客户蓝V认证+对应能力审核通过）后按本文立项。
> 背景：客户后续可能申请蓝V账号，本文明确届时能解锁什么、改哪里、按什么顺序申请。

## 0. 先厘清两道门（与docs/11一致）
| 门 | 属性 | 蓝V能否解决 |
|---|---|---|
| 开发者主体（建应用/OAuth密钥） | 做软件的公司，企业营业执照 | **否** —— 蓝V是抖音号的认证，不是开发者资质 |
| 授权账号（被绑定的抖音号） | 蓝V=企业号 | **是** —— 这道门就是蓝V本身 |

结论：蓝V解锁的是「账号侧能力」；开发者侧企业主体仍然必须（S23遗留前置不变）。

## 1. 蓝V后解锁清单（按价值排序，均需逐项申请）
| # | 能力 | 解锁的产品面 | 申请确定性 |
|---|---|---|---|
| B1 | 企业号私信/客服消息 | `messages`页从占位→真会话；`imEnabled`评估翻转 | 需能力申请+审核，届时复查 |
| B2 | 企业号评论能力 `video.comment`（实时评论列表） | 评论实时化，webhook外的第二数据源 | ⚠️ 查证时为"内测名额已满暂停申请"，届时复查 |
| B3 | 企业号数据/粉丝画像类 scope | 看板`净增粉/粉丝画像`从mock→真 | 中，随数据开放服务申请 |
| B4 | 事件订阅（Webhooks） | 评论事件实时入队→即时接待 | 中，需公网HTTPS回调 |
| B5 | 抖音企业号开放能力（官方企业号API） | 菜单/POI/线索等经营组件 | 中，按需申请 |

## 2. 代码改动点（当前已预留的开关位置）
1. `config/app.config.ts` — `imEnabled: false` P0红线：**翻开关的三前置**=B1能力审批通过 + MEMORY红线流程 + 版本号升级（verify-config有不变式校验：`app.imEnabled=false`，翻转需同步改verify并说明依据）
2. `app/messages/page.tsx` — 占位页（当前只读提示）→真会话列表+只读辅助，接入B1接口
3. `lib/douyinPort.ts` — 追加 `fetchImMessages/pushImReply` 等方法（mock/live双实现，结构同S23）
4. `config/auth.config.ts` — `requiredScopes`扩充企业号scope（注释已标：改动需重审）
5. `app/auth/page.tsx` — 「蓝V·去升级」链接已有落点，届时挂申请指引
6. `docs/10` C类封存项**不受蓝V影响**：爬取他人数据/批量自动群发仍需双签，蓝V不豁免

## 3. 届时申请顺序（预计2–4周）
1. 蓝V认证通过（客户侧，1–3工作日）
2. 复查B2"内测名额"状态 → 提交B1/B3/B4能力申请（5–7工作日/项，可并行）
3. S23的live模式切通（企业主体密钥）→ 与蓝V能力同应用挂载
4. 按§2顺序改造，每翻一个开关跑全量质检门
5. B1上线前：私信话术合规复审（自动回复=自动化范畴，遵守08红线：默认人工辅助）

## 4. 边界重申
- 蓝V≠自动私信许可证：即使B1开通，**自动外呼/批量主动私信仍属08封存区**；本路径只做"被动会话的辅助接待"
- 个人号路径不受影响：docs/03的个人号降级策略保持，双轨并存
